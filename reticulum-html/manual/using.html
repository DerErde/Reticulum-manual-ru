Использование Reticulum в вашей системе¶

Reticulum не устанавливается как драйвер или модуль ядра, как можно было бы ожидать от сетевого стека. Вместо этого Reticulum распространяется как модуль Python, содержащий сетевое ядро, набор утилит и программ-демонов.

Это означает, что для его установки или использования не требуется никаких особых привилегий. Он также очень легковесен и его легко переносить и устанавливать на новые системы.

Когда Reticulum установлен, любая программа или приложение, использующее Reticulum, автоматически загрузит и инициализирует Reticulum при запуске, если он ещё не запущен.

Во многих случаях такого подхода достаточно. Когда какой-либо программе нужно использовать Reticulum, он загружается, инициализируется, поднимаются интерфейсы, и программа может общаться через любые доступные сети Reticulum. Если запускается другая программа и также хочет получить доступ к той же сети Reticulum, уже запущенный экземпляр просто используется совместно. Это работает для любого количества одновременно запущенных программ и очень удобно, но в зависимости от вашего сценария использования есть и другие варианты.

Примечание переводчика

Идентичность (Identity) — в сетевых и распределённых системах (особенно в контексте ZeroMQ, IPC, AMQP, WebRTC) это уникальное сочетание характеристик источника: его адрес, порт, тип транспорта, а часто и динамически сгенерированное криптографическое имя.

1) С английского языка фразу Identity file можно перевести как файл идентичности.

Что такое Identity file в контексте Reticulum?

Файл идентичности — это ваш цифровой идентификатор в сети Reticulum. Он представляет собой небольшой файл (всего 64 байта), в котором хранятся два ваших секретных ключа:

  • Приватный ключ X25519 (32 байта): используется для шифрования данных, которые вам отправляют. Он гарантирует, что только вы сможете их прочитать.
  • Приватный ключ Ed25519 (32 байта): используется для создания цифровых подписей. Он гарантирует, что сообщения, отправленные вами, не будут подделаны в пути.

Файл с приватным ключом находится по пути: ~/.reticulum/storage/identities

Вы спросите: а почему именно файл идентичности, а не просто идентификатор?
Потому что в Reticulum это не просто имя или номер, а полноценный криптографический объект.

Для простоты файл идентичности можно называть файлом ключей, но в тексте мы сохраним оригинальный термин.

2) В Reticulum существуют два вида файлов идентичности:

Общего назначения — находятся в ~/.reticulum/storage/identities. Используются вами вручную или через утилиту rnid.

Привязанные к конкретным программам — например, ~/.reticulum/identities/rnx для утилиты rnx. Такие файлы создаются автоматически при первом запуске программы и используются только ей.

Разделение сделано ради безопасности, гибкости и изоляции: компрометация ключа от одной программы не даст доступа к другим вашим данным. Использовать разные идентичности безопаснее, но при желании можно обойтись и одной.

Вы можете либо полагаться на автоматически созданные идентичности, либо указать путь к собственному файлу через параметр -i.

3) Термин Blackhole management дословно переводится как управление чёрными дырами, но мы будем использовать более понятный вариант: управление чёрными списками

Термины:
Инициатор — тот, кто подключается (клиент).
Прослушиватель — тот, кто ждёт подключений (сервер).

Конфигурация и данные¶

Reticulum хранит всю информацию, необходимую для работы, в единственной директории файловой системы. При запуске Reticulum будет искать действительную конфигурационную директорию в следующих местах:

  • /etc/reticulum

  • ~/.config/reticulum

  • ~/.reticulum

Если существующая конфигурационная директория не найдена, создаётся директория ~/.reticulum, и здесь автоматически создаётся конфигурация по умолчанию. При желании вы можете переместить её в одно из других мест.

Также можно использовать совершенно произвольные конфигурационные директории, указав соответствующие параметры командной строки при запуске программ на основе Reticulum. Вы также можете запускать несколько отдельных экземпляров Reticulum на одной физической системе, либо изолированно друг от друга, либо соединив их вместе.

В большинстве случаев одной физической системе потребуется запускать только один экземпляр Reticulum. Его можно либо запускать при загрузке как системную службу, либо просто поднимать, когда он нужен программе. В любом случае, любое количество программ, работающих в одной системе, будут автоматически совместно использовать один экземпляр Reticulum, если конфигурация это позволяет, а по умолчанию так и есть.

Вся конфигурация Reticulum находится в файле ~/.reticulum/config. При первом запуске Reticulum в новой системе создаётся базовый, но полностью функциональный конфигурационный файл. Конфигурация по умолчанию выглядит так:

# Это конфигурационный файл Reticulum по умолчанию.
# Вероятно, вам следует отредактировать его, чтобы добавить
# любые дополнительные интерфейсы и настройки, которые могут понадобиться.

# В эту конфигурацию по умолчанию включены только самые базовые
# опции. Чтобы увидеть более подробный и гораздо более длинный
# пример конфигурации, вы можете выполнить команду:
# rnsd --exampleconfig


[reticulum]

# Если вы включите транспорт, ваша система будет маршрутизировать
# трафик для других участников, передавать объявления и обслуживать
# запросы путей. Это следует делать для систем, которые подходят
# для роли транспортных узлов, т.е. если они стационарны и
# постоянно включены. Эта директива необязательна и может быть
# удалена для краткости.

enable_transport = No


# По умолчанию первая программа, запускающая Сетевой Стек
# Reticulum, создаст общий экземпляр, с которым могут
# взаимодействовать другие программы. Только общий экземпляр
# открывает все настроенные интерфейсы напрямую, а другие
# локальные программы взаимодействуют с общим экземпляром через
# локальный сокет. Это полностью прозрачно для пользователя
# и, как правило, должно быть включено. Эта директива
# необязательна и может быть удалена для краткости.

share_instance = Yes


# Если вы хотите запустить несколько *разных* общих экземпляров
# в одной системе, вам нужно будет указать разные
# имена экземпляров для каждого. На платформах, поддерживающих
# доменные сокеты, это можно сделать с помощью опции instance_name:

instance_name = default

# Некоторые платформы не поддерживают доменные сокеты, и в таком
# случае вы можете изолировать разные экземпляры, указав
# уникальный набор портов для каждого:

# shared_instance_port = 37428
# instance_control_port = 37429


# Если вы хотите явно использовать TCP для связи 
# с общим экземпляром вместо доменных сокетов, 
# это также возможно с помощью следующей опции: 

# shared_instance_type = tcp


# В системах, где запущенные экземпляры могут не иметь доступа
# к одной и той же общей конфигурационной директории Reticulum,
# всё ещё можно обеспечить полную интерактивность для
# запущенных экземпляров, вручную указав общий ключ RPC.
# Почти во всех случаях эта опция не нужна, но она
# может быть полезна в таких ОС, как Android.
# Ключ должен быть указан в виде байтов в шестнадцатеричном формате.

# rpc_key = e5c032d3ec4e64a6aca9927ba8ab73336780f6d71790


# Можно разрешить удалённое управление системами
# Reticulum с помощью различных встроенных утилит, таких как
# rnstatus и rnpath. Вам нужно будет указать один или
# несколько хешей Reticulum Identity для аутентификации
# запросов от клиентских программ. Для этой цели вы можете
# использовать ваши криптографические ключи - Identity files или сгенерировать
# новые с помощью утилиты rnid.

# enable_remote_management = yes
# remote_management_allowed = 9fb6d773498fb3feda407ed8ef2c3229, 2d882c5586e548d79b5af27bca1776dc


# Вы можете настроить Reticulum на аварийное завершение и
# принудительное закрытие, если произойдёт неисправимая ошибка
# интерфейса, например, исчезновение аппаратного устройства
# интерфейса. Это необязательная директива, которую можно
# опустить для краткости. По умолчанию это поведение отключено.

# panic_on_interface_error = No


# Когда транспорт включён, можно разрешить Транспортному
# Экземпляру отвечать на пробные запросы от утилиты
# rnprobe. Это может быть полезным инструментом для проверки
# связности. Когда эта опция включена, пробный пункт назначения
# будет сгенерирован из идентичности транспортного экземпляра
# и выведен в журнал при запуске.
# Опционально, по умолчанию отключено.

# respond_to_probes = No


[logging]
# Допустимые уровни логирования от 0 до 7:
#   0: Логировать только критическую информацию
#   1: Логировать ошибки и более низкие уровни
#   2: Логировать предупреждения и более низкие уровни
#   3: Логировать уведомления и более низкие уровни
#   4: Логировать информацию и ниже (по умолчанию)
#   5: Подробное логирование
#   6: Отладочное логирование
#   7: Экстремальное логирование

loglevel = 4


# Секция interfaces определяет физические и виртуальные
# интерфейсы, которые Reticulum будет использовать для связи.
# Эта секция будет содержать примеры для различных типов
# интерфейсов. Вы можете изменить их или использовать как
# основу для собственной конфигурации, либо просто удалить
# неиспользуемые.

[interfaces]

  # Этот интерфейс обеспечивает связь с другими
  # локальными узлами Reticulum через UDP. Ему не
  # нужна какая-либо функциональная IP-инфраструктура,
  # такая как маршрутизаторы или DHCP-серверы, но
  # потребуется, чтобы в вашей ОС был включён хотя бы
  # локальный IPv6, что должно быть включено по умолчанию
  # практически в любой ОС. Смотрите Руководство Reticulum
  # для получения дополнительных опций конфигурации.

  [[Default Interface]]
    type = AutoInterface
    interface_enabled = True

Если инфраструктура Reticulum уже существует локально, вам, вероятно, не нужно ничего менять, и вы уже можете быть подключены к более широкой сети. Если нет, вам, вероятно, потребуется добавить соответствующие интерфейсы в конфигурацию, чтобы общаться с другими системами.

Вы можете сгенерировать более подробный пример конфигурации, выполнив команду:

rnsd --exampleconfig

Вывод включает примеры для большинства типов интерфейсов, поддерживаемых Reticulum, а также дополнительные опции и параметры конфигурации.

Рекомендуется прочитать комментарии и пояснения в приведённой выше конфигурации по умолчанию. Это познакомит вас с основными концепциями, необходимыми для настройки вашей сети. Как только вы это сделаете, загляните в главу Интерфейсы этого руководства.

Встроенные служебные программы¶

Reticulum включает ряд полезных утилит как для управления вашими сетями Reticulum, так и для выполнения общих задач в сетях Reticulum, таких как передача файлов на удалённые системы и удалённое выполнение команд и программ.

Если вы часто используете Reticulum из нескольких разных программ или просто хотите, чтобы Reticulum был постоянно доступен, например, если вы размещаете транспортный узел, вы можете запустить Reticulum как отдельную службу, которую могут использовать другие программы, приложения и сервисы.

Утилита rnsd¶

Запустить Reticulum как службу очень просто. Достаточно выполнить встроенную команду rnsd. Когда rnsd запущен, он будет держать все настроенные интерфейсы открытыми, обрабатывать транспорт, если он включён, и позволять любым другим программам немедленно использовать сеть Reticulum, для которой он настроен.

Вы даже можете запускать несколько экземпляров rnsd с разными конфигурациями в одной системе.

Примеры использования

Запуск rnsd:

$ rnsd

[2023-08-18 17:59:56] [Notice] Started rnsd version 0.5.8

Запуск rnsd в режиме службы, при котором весь вывод логирования направляется прямо в файл:

$ rnsd -s

Сгенерируйте подробный и детальный пример конфигурации с пояснениями всех параметров настройки и примерами конфигурации интерфейсов:

$ rnsd --exampleconfig

Все параметры командной строки

usage: rnsd.py [-h] [--config CONFIG] [-v] [-q] [-s] [--exampleconfig] [--version]

Reticulum Network Stack Daemon

options:
  -h, --help        показать эту справку и выйти
  --config CONFIG   путь к альтернативной конфигурационной директории Reticulum
  -v, --verbose
  -q, --quiet
  -s, --service     rnsd запущен как служба и должен логировать в файл
  -i, --interactive перейти в интерактивную оболочку после инициализации
  --exampleconfig   вывести подробный пример конфигурации в stdout и выйти
  --version         показать номер версии программы и выйти

Вы можете легко добавить rnsd в качестве постоянно работающей службы, настроив соответствующий сервис.

Утилита rnid¶

С помощью утилиты rnid вы можете создавать, управлять и просматривать Идентичности Reticulum. Программа может вычислять хеши пунктов Назначений, а также выполнять шифрование и дешифрование файлов.

Используя rnid, можно асимметрично шифровать файлы и информацию для любого хеша назначения Reticulum [т.е. для получателя], а также создавать и проверять криптографические подписи.

Примеры использования

Создать новую идентичность:

$ rnid -g ./new_identity

Показать информацию о ключах идентичности:

$ rnid -i ./new_identity -p

Loaded Identity <984b74a3f768bef236af4371e6f248cd> from new_id
Public Key  : 0f4259fef4521ab75a3409e353fe9073eb10783b4912a6a9937c57bf44a62c1e
Private Key : Hidden

Зашифровать файл для пользователя LXMF:

$ rnid -i 8dd57a738226809646089335a6b03695 -e my_file.txt

Recalled Identity <bc7291552be7a58f361522990465165c> for destination <8dd57a738226809646089335a6b03695>

Утилита rnprobe¶

Утилита rnprobe позволяет вам проверять связь с пунктом назначения, аналогично программе ping. Обратите внимание, что ответ на пробные запросы будет отправлен только в том случае, если указанный пункт назначения настроен на отправку подтверждений для полученных пакетов. У большинства пунктов назначения эта опция не включена, поэтому большинство из них не будут отвечать на пробные запросы.

Вы можете включить ответы на пробные запросы в транспортном экземпляре Reticulum, установив директиву конфигурации respond_to_probes. После этого при запуске транспортного экземпляра в лог будет выведен пробный пункт назначения — пробный адрес для проверки связи.

Примеры использования

Проверить связь с пунктом назначения:

$ rnprobe rnstransport.probe 2d03725b327348980d570f739a3a5708

Sent 16 byte probe to <2d03725b327348980d570f739a3a5708>
Valid reply received from <2d03725b327348980d570f739a3a5708>
Round-trip time is 38.469 milliseconds over 2 hops

Отправить пробный запрос большего размера:

$ rnprobe rnstransport.probe 2d03725b327348980d570f739a3a5708 -s 256

Sent 16 byte probe to <2d03725b327348980d570f739a3a5708>
Valid reply received from <2d03725b327348980d570f739a3a5708>
Round-trip time is 38.781 milliseconds over 2 hops

Если интерфейс, принимающий ответы на пробные запросы, поддерживает передачу таких радиопараметров, как RSSI и SNR, утилита rnprobe также выведет их в составе результата.

$ rnprobe rnstransport.probe e7536ee90bd4a440e130490b87a25124

Sent 16 byte probe to <e7536ee90bd4a440e130490b87a25124>

Утилита rngit¶

Утилита rngit предоставляет полноценный хостинг репозиториев Git и взаимодействие с ними через Reticulum, а также множество других полезных возможностей для разработки, совместной работы и публикации. Она позволяет размещать Git-репозитории на узлах Reticulum, взаимодействовать с удалёнными репозиториями с помощью стандартных команд Git через схему URL rns://, а также публиковать релизы программного обеспечения.

Система состоит из двух частей: узел rngit, который размещает репозитории и управляет ими, и вспомогательная программа git-remote-rns, которая позволяет Git взаимодействовать с узлами rngit. Как только RNS установлен в вашей системе, вы можете прозрачно использовать Git с репозиториями, размещёнными в Reticulum, точно так же, как и с любым другим типом удалённого репозитория.
Git поверх Reticulum использует URL следующего формата: rns://DESTINATION_HASH/group/repo.

Если вы настроите ветку на отслеживание удалённого репозитория Reticulum в качестве источника по умолчанию, вы можете просто использовать git как обычно — все команды работают прозрачно и ожидаемым образом.

Предупреждение

Программа rngit — это новое дополнение к RNS! Данная функция была введена в версии RNS 1.2.0. Хотя при проектировании было уделено большое внимание созданию безопасной, но при этом гибко настраиваемой системы разрешений, позволяющей множеству пользователей взаимодействовать с множеством различных репозиториев на одном узле, rngit ещё не был тщательно протестирован в реальных условиях! Будьте осторожны при размещении репозиториев, особенно если они являются публичными или полупубличными.

Полную документацию по системе rngit смотрите в главе Git поверх Reticulum этого руководства.

Утилита rnsh¶

Утилита rnsh предоставляет полноценную интерактивную удалённую оболочку поверх Reticulum. Она позволяет устанавливать зашифрованные, аутентифицированные сеансы оболочки на удалённых системах с полноценной эмуляцией терминала, поддержкой каналов (pipe) и изменением размера окна.

В то время как утилита rnx полезна для простого удалённого выполнения команд и получения вывода, rnsh обеспечивает полноценное интерактивное терминальное взаимодействие, что делает её идеальной для задач удалённого администрирования и управления, требующих взаимодействия в реальном времени — точно так же, как SSH для IP-сетей.

rnsh работает в двух режимах: режим прослушивателя, принимающий входящие подключения, и режим инициатора, который подключается к удалённому прослушивателю. Обе стороны аутентифицируются с использованием идентичностей Reticulum, гарантируя, что только авторизованные участники могут устанавливать сеансы.

Примечание

rnsh предоставляет настоящий интерактивный терминал поверх Reticulum. Он поддерживает полную эмуляцию терминала, включая escape-последовательности, изменение размера окна, проброс сигналов, а также перенаправление стандартных потоков ввода, вывода и ошибок. Это делает его пригодным для запуска текстовых редакторов, терминальных мультиплексоров и любых других интерактивных программ на удалённых системах.

Примеры использования

Запустите rnsh в режиме прослушивателя, принимая подключения от определённых идентичностей:

$ rnsh -l -a 941bed5e228775e5a8079fc38b1ccf3f -a 1b03013c25f1c2ca068a4f080b844a10

Вы также можете указать разрешённые хеши идентичностей (по одному в строке) в файле ~/.rnsh/allowed_identities или ~/.config/rnsh/allowed_identities и просто запустить программу в режиме прослушивания:

$ rnsh -l

Подключитесь к удалённому прослушивателю с другого компьютера:

$ rnsh 7a55144adf826958a9529a3bcf08b149

Укажите команду, которая будет запускаться при подключении, если инициатор не передал свою, или когда удалённое выполнение команд отключено, отделив параметры rnsh от удалённой команды с помощью --:

$ rnsh 7a55144adf826958a9529a3bcf08b149 -- top

Задайте команду по умолчанию для прослушивателя на случай, если инициатор не укажет свою, или когда удалённое выполнение команд отключено:

$ rnsh -l -- /bin/bash --login

Используйте флаг -m, чтобы зеркалировать код возврата удалённого процесса:

$ rnsh -m 7a55144adf826958a9529a3bcf08b149 -- /usr/local/bin/check-status

Используйте флаг -p, чтобы отобразить идентичность и хеш пункта назначения для прослушивателя:

$ rnsh -l -p

Используйте определённый файл идентичности вместо файла по умолчанию:

$ rnsh -l -i /path/to/identity

Объявить пункт назначения прослушивателя при запуске, а затем повторять объявление с заданным интервалом:

$ rnsh -l -b 900

Параметр -b задаёт период объявлений в секундах. Используйте 0, чтобы объявить только один раз при запуске.

Аутентификация и авторизация

По умолчанию rnsh требует, чтобы подключающиеся инициаторы идентифицировали себя с помощью идентичности Reticulum, хеш которой присутствует в списке разрешённых идентичностей. Разрешённые идентичности можно указать в командной строке с помощью параметра -a, который можно использовать многократно:

$ rnsh -l -a 941bed5e228775e5a8079fc38b1ccf3f -a 1b03013c25f1c2ca068a4f080b844a10

Вы также можете вести список разрешённых хешей идентичностей в файле ~/.rnsh/allowed_identities или ~/.config/rnsh/allowed_identities, по одному шестнадцатеричному хешу в строке. Этот файл перезагружается при каждом новом подключении, поэтому изменения вступают в силу немедленно, без перезапуска rnsh.

Если вы хотите принимать подключения от любой идентичности (для тестирования или в полностью доверенных средах), вы можете отключить аутентификацию с помощью параметра -n:

$ rnsh -l -n

Предупреждение

Отключение аутентификации с помощью -n означает, что любой участник Reticulum, способный достичь вашего прослушивателя, сможет выполнять команды в вашей системе. Используйте эту опцию, только если вы действительно понимаете, что делаете.

Управление удалёнными командами

При работе в режиме прослушивателя rnsh позволяет вам управлять тем, как обрабатываются удалённые команды:

  • По умолчанию прослушиватель принимает команду, отправленную инициатором. Если инициатор не передаёт команду, используется оболочка прослушивателя по умолчанию.

  • Используйте -C (--no-remote-command), чтобы отключить выполнение команд, полученных от инициатора. Будет выполнена только команда прослушивателя по умолчанию (или команда, указанная после --):

$ rnsh -l -C -- /usr/local/bin/safe-script

  • Используйте -A (--remote-command-as-args), чтобы добавить команду инициатора к команде прослушивателя по умолчанию вместо её замены. Это может быть полезно для ограничения удалённого доступа конкретной программой, при этом позволяя инициатору передавать аргументы:

$ rnsh -l -A -- /usr/bin/top

Имена служб

При работе в режиме прослушивателя rnsh использует имя службы (service name), чтобы различать несколько экземпляров прослушивателя, которые могут использовать одну и ту же идентичность. По умолчанию именем службы является default. Вы можете указать другое имя службы с помощью параметра -s:

$ rnsh -l -s monitoring

Это позволяет запускать несколько прослушивателей на одном узле, каждый со своим именем службы и назначением.

Параметры инициатора

При подключении к удалённому прослушивателю доступны несколько параметров:

  • Используйте -N (--no-id), чтобы отключить отправку вашей идентичности удалённому прослушивателю. Обратите внимание, что в этом случае для успешного подключения на прослушивателе должна быть отключена аутентификация (-n).

  • Используйте -m (--mirror), чтобы инициатор возвращал код выхода удалённого процесса, а не всегда возвращал 0.

  • Используйте -w (--timeout), чтобы указать тайм-аут подключения и запроса в секундах. По умолчанию тайм-аут соответствует тайм-ауту запроса пути в Reticulum.

Идентичность и пункт назначения

Файл идентичности по умолчанию для rnsh хранится по адресу ~/.reticulum/identities/rnsh, но вы можете указать другой с помощью параметра -i, который будет создан, если он ещё не существует:

$ rnsh -l -i /path/to/identity

Чтобы отобразить информацию об идентичности и пункте назначения для прослушивателя, используйте параметр -p. В сочетании с -l отображаются как идентичность, так и хеш пункта назначения прослушивателя:

$ rnsh -p

Идентичность     : <984b74a3f768bef236af4371e6f248cd>

$ rnsh -l -p

Идентичность     : <984b74a3f768bef236af4371e6f248cd>
Прослушивание на : 7a55144adf826958a9529a3bcf08b149

Подробность вывода

Как и другие утилиты Reticulum, rnsh поддерживает флаги -v и -q для повышения или понижения уровня детализации журнала. Можно указать несколько флагов, чтобы дополнительно настроить уровень журналирования. Уровень журнала по умолчанию — INFO для прослушивателей и ERROR для инициаторов.

$ rnsh -l -vv       # Прослушиватель с отладочным уровнем вывода
$ rnsh -q 7a55144adf826958a9529a3bcf08b149   # Тихий инициатор

По умолчанию весь вывод журнала для инициаторов направляется в ~/.rnsh/logfile.

Обнаружение интерфейсов¶

Reticulum включает встроенную функциональность для обнаружения интерфейсов, к которым можно подключиться, через сам Reticulum. Это особенно полезно в ситуациях, когда вы хотите выполнить одно или несколько из следующих действий:

  • Обнаружить точки входа, доступные в Интернете

  • Найти доступные радио-точки для доступа, в физическом мире

  • Поддерживать связь с экземплярами RNS с неизвестными или меняющимися IP-адресами

Обнаруженные интерфейсы могут быть автоматически подключены Reticulum, что позволяет создавать конфигурации, где произвольный интерфейс может действовать просто как начальное соединение, которое может быть разорвано, как только будут обнаружены и подключены более подходящие интерфейсы.

Механизм обнаружения интерфейсов использует объявления, отправляемые через сам Reticulum, и поддерживает как публично читаемые интерфейсы, так и приватное, зашифрованное обнаружение, которое может быть расшифровано только указанными сетевыми идентичностями. Также можно указать, какие сетевые идентичности следует считать действительными источниками для обнаруженных интерфейсов, чтобы интерфейсы, опубликованные неизвестными сущностями, игнорировались.

Примечание

Сетевая идентичность (network identity) — это обычный набор ключей идентичности Reticulum, который может использоваться одним или несколькими транспортными узлами для обозначения их принадлежности к одной общей сети. В контексте обнаружения интерфейсов это упрощает управление подключением только к тем конкретным сетям, которые вас интересуют, даже если эти сети используют множество отдельных физических транспортных узлов.

Это также делает удобным автоматическое подключение обнаруженных интерфейсов только для сетей, к которым у вас есть определённый уровень доверия.

Для информации о том, как сделать ваши интерфейсы обнаруживаемыми, смотрите главу Обнаруживаемые интерфейсы этого руководства. Текущий раздел будет сосредоточен на том, как фактически обнаруживать и подключаться к интерфейсам, доступным в сети.

В своей самой базовой форме для включения обнаружения интерфейсов достаточно просто установить для параметра discover_interfaces значение true в вашей конфигурации Reticulum:

[reticulum]
...
discover_interfaces = yes
...

[ для включения установите значение: YES ]

Как только эта опция включена, ваш экземпляр RNS начнёт прослушивать объявления об обнаружении интерфейсов и сохранять их для последующего использования или проверки. Вы можете вывести список обнаруженных интерфейсов с помощью утилиты rnstatus: 

$ rnstatus -d

RNS Amsterdam  Backbone  ✓ Доступен  32m ago      16     52.3865, 4.9037

В дополнение к предоставлению информации об обнаружении локальных интерфейсов и управлении ими, утилита rnstatus может экспортировать данные обнаруженных интерфейсов в машиночитаемом формате JSON с помощью опции rnstatus -d --json. Это может быть полезно для экспорта данных во внешние приложения, такие как страницы статуса, карты точек доступа и тому подобное.

Чтобы контролировать, какие источники считаются допустимыми для обнаруженных интерфейсов, для системы обнаружения интерфейсов можно задать дополнительные параметры конфигурации.

  • Опция interface_discovery_sources представляет собой список сетевых или транспортных идентичностей, от которых будут приниматься интерфейсы. Если эта опция установлена, все остальные источники будут игнорироваться. Если эта опция не установлена, обнаруженные интерфейсы будут приниматься от любого источника, но всё равно будут зависеть от требований к значению метки.

  • Опция required_discovery_value задаёт минимальное значение метки, необходимое для того, чтобы объявление интерфейса считалось валидным. Чтобы сделать вычислительно сложным спам сети большим количеством неработающих или вредоносных интерфейсов, каждый объявляемый интерфейс требует действительной криптографической метки с настраиваемым уровнем сложности.

  • Значение autoconnect_discovered_interfaces по умолчанию равно 0 и задаёт максимальное количество обнаруженных интерфейсов, которые должны быть автоматически подключены в любой момент времени. Если установлено число больше 0, Reticulum автоматически управляет подключениями обнаруженных интерфейсов и будет поднимать и опускать обнаруженные интерфейсы в зависимости от доступности. Вы можете в любое время добавить обнаруженные интерфейсы в свою конфигурацию вручную, чтобы постоянно держать их доступными.

  • Опция network_identity задаёт сетевую идентичность для этого экземпляра RNS. Эта идентичность используется как для подписи (и, при необходимости, шифрования) исходящих объявлений об обнаружении интерфейсов, так и для расшифровки входящей информации об обнаружении.

Приведённый ниже фрагмент конфигурации содержит пример установки этих дополнительных опций:

[reticulum]
...
discover_interfaces = yes
interface_discovery_sources = 521c87a83afb8f29e4455e77930b973b
required_discovery_value = 16
autoconnect_discovered_interfaces = 3
network_identity = ~/.reticulum/storage/identities/my_network
...

Удалённое управление¶

Можно разрешить удалённое управление системами Reticulum с помощью различных встроенных утилит, таких как rnstatus и rnpath. Для этого вам нужно установить директиву enable_remote_management в секции [reticulum] конфигурационного файла. Вам также нужно будет указать один или несколько хешей идентичностей Reticulum для аутентификации запросов от клиентских программ. Для этой цели вы можете использовать существующие файлы идентичностей или сгенерировать новые с помощью утилиты rnid.

Ниже приведён сокращённый пример включения удалённого управления в конфигурационном файле Reticulum:

[reticulum]
...
enable_remote_management = yes
remote_management_allowed = 9fb6d773498fb3feda407ed8ef2c3229, 2d882c5586e548d79b5af27bca1776dc
...

Для полного примера конфигурации вы можете выполнить rnsd --exampleconfig.

Управление чёрными списками¶

Сети Reticulum принципиально бесправны и открыты, позволяя любому желающему с совместимым интерфейсом участвовать. Хотя эта открытость важна для устойчивой и децентрализованной сети, она также подвергает сеть потенциальным злоупотреблениям, таким как заполнение сети избыточными широковещательными объявлениями или другими формами исчерпания ресурсов.

Система Чёрных списков предоставляет инструменты для управления этой проблемой. Она позволяет операторам и отдельным пользователям блокировать определённые идентичности на Транспортном уровне, предотвращая распространение их объявлений через ваш узел и доступ других узлов к ним через вашу сеть.

Важно

Принципиально нет способа глобально заблокировать или подвергнуть цензуре какую-либо идентичность или пункт назначения в сетях Reticulum. Функция чёрных списков лишь предотвращает объявления от (и трафик к) всех пунктов назначения, связанных с заблокированной идентичностью, только в ваших собственных сегментах сети.

Это предоставляет пользователям и операторам контроль над тем, что они хотят разрешить в своих собственных сегментах сети, но нет способа глобально цензурировать или удалить идентичность, пока кто-то готов предоставить для неё транспорт.

Эта функциональность служит двойной цели:

  • Для отдельных пользователей: Она предлагает простой способ поддерживать тихую и эффективную локальную сеть, вручную блокируя спамящих или нежелательных участников.

  • Для сетевых операторов: Она позволяет создавать федеративные, общесетевые стандарты безопасности. Публикуя и распространяя черные списки, операторы могут защищать крупные инфраструктуры и распределять правила фильтрации спама по mesh-сети без ручного вмешательства.

Локальное управление чёрными списками¶

Наиболее прямой способ управления нежелательными идентичностями — ручная настройка с помощью утилиты rnpath. Это позволяет вам мгновенно блокировать или разблокировать конкретные идентичности на вашем локальном Транспортном Экземпляре.

Добавление идентичности в чёрный список

Чтобы заблокировать идентичность, используйте флаг -B (или --blackhole), за которым следует хеш идентичности. Вы можете опционально указать длительность и причину, что полезно для логирования и будущих справок.

$ rnpath -B 3a4f8b9c1d2e3f4g5h6i7j8k9l0m1n2o

Вы также можете добавить длительность (в часах) и причину:

$ rnpath -B 3a4f8b9c1d2e3f4g5h6i7j8k9l0m1n2o --duration 24 --reason "Excessive announces"

Снятие блокировки

Чтобы удалить идентичность из чёрного списка, используйте флаг -U (или --unblackhole):

$ rnpath -U 3a4f8b9c1d2e3f4g5h6i7j8k9l0m1n2o

Просмотр чёрного списка

Чтобы увидеть все идентичности, в данный момент заблокированные на вашем локальном экземпляре, используйте флаг -b (или --blackholed):

$ rnpath -b

<3a4f8b9c1d2e3f4g5h6i7j8k9l0m1n2o> заблокирован на 23ч, 56м (Excessive announces)
<399ea050ce0eed1816c300bcb0840938> заблокирован бессрочно (Announce spam)
<d56a4fa02c0a77b3575935aedd90bdb2> заблокирован бессрочно (Announce spam)
<2b9ec651326d9bc274119054c70fb75e> заблокирован бессрочно (Announce spam)
<1178a8f1fad405bf2ad153bf5036bdfd> заблокирован бессрочно (Announce spam)

Автоматическое получение списков¶

Ручная блокировка идентичностей эффективна для немедленных угроз, но поддержание актуального блок-листа для большой сети непрактично. Reticulum поддерживает автоматическое получение списков, позволяя вашему узлу подписываться на список блокировки, поддерживаемые доверенными участниками, или центральным узлом, которым вы управляете сами.

Предупреждение

Проверяйте перед подпиской! Подписка на источник чёрных списков — это мощное действие, которое предоставляет этому источнику возможность диктовать, с кем вы можете общаться. Прежде чем добавлять источник в свою конфигурацию, убедитесь, что его подходы соответствуют вашей политике использования и ценностям. Слепая подписка на непроверенные списки может непреднамеренно заблокировать законных участников или важные службы.

Когда эта функция включена, ваш Транспортный Экземпляр будет периодически (примерно раз в час) подключаться к настроенным источникам, загружать их актуальные чёрные списки и автоматически объединять их с вашим локальным списком блокировки. Это обеспечивает защиту по принципу «настроил и забыл» как для отдельных пользователей, так и для крупных сетей.

Конфигурация

Чтобы включить автоматическое получение, добавьте опцию blackhole_sources в раздел [reticulum] вашего конфигурационного файла. Этот параметр принимает список хешей транспортных идентичностей, разделённый запятыми, которым вы доверяете как источникам доверенных чёрных списков.

[reticulum]
...
# Автоматически загружать чёрные списки из этих доверенных источников
blackhole_sources = 521c87a83afb8f29e4455e77930b973b, 68a4aa91ac350c4087564e8a69f84e86
...

Как это работает

  1. Когда эта функция включена, служба BlackholeUpdater работает в фоновом режиме.

  2. Для каждого хеша идентичности, перечисленного в blackhole_sources, она пытается установить временное соединение с его соответствующим назначением rnstransport.info.blackhole.

  3. Она запрашивает путь /list, который возвращает словарь заблокированных идентичностей и связанных с ними метаданных.

  4. Полученный список объединяется с вашей локальной базой данных blackholed_identities.

  5. Списки сохраняются на диск, что гарантирует их сохранность при перезапусках.

Примечание

Вы можете проверить внешние списки, на которые вы подписаны, и их содержимое, не импортируя их, используя rnpath -p. Смотрите документацию по утилите rnpath для получения подробной информации о запросе удалённых чёрных списков.

Публикация черных списков¶

Если вы управляете публичным шлюзом, общественным хабом или просто хотите поделиться своим чёрным списком с другими, вы можете настроить свой экземпляр на публикацию чёрных списков. Это позволяет другим узлам подписываться на ваши определения нежелательного трафика.

Включение публикации

Чтобы опубликовать ваш локальный чёрный список, включите опцию publish_blackhole в секции [reticulum]:

[reticulum]
...
publish_blackhole = yes
...

Когда это включено, ваш Транспортный Экземпляр зарегистрирует обработчик запросов по адресу rnstransport.info.blackhole. Любой участник, подключившийся к этому назначению и запросивший /list, получит полный набор идентичностей, присутствующих в вашей локальной базе чёрных списков.

Федерация и доверие

Система чёрных списков опирается на доверительные отношения между подписчиком и издателем. Подписываясь на источник, вы неявно доверяете ему блокировать только те идентичности, которые действительно вредны для сети.

По мере развития экосистемы эта система спроектирована для интеграции с Сетевыми Идентичностями. Это позволяет сообществам проверять, что опубликованный чёрный список действительно предоставлен определённой сетью или организацией с определённым уровнем репутации и надёжности, добавляя уровень криптографического доверия к процессу федерации. Это предотвращает публикацию злоумышленниками поддельных списков, предназначенных для цензуры законного трафика.

Для операторов это создаёт масштабируемую модель, в которой поддержание одного высококачественного блок-листа может защитить тысячи нижестоящих участников, значительно сокращая административную нагрузку.

Если вы настраиваете систему для постоянного использования с Reticulum, есть несколько изменений в конфигурации системы, которые могут облегчить администрирование. Эти изменения будут подробно описаны здесь.

Фиксированные имена последовательных портов¶

В экземпляре Reticulum с несколькими интерфейсами на основе последовательных портов может быть полезно использовать фиксированные имена устройств для последовательных портов вместо динамически назначаемых сокращений, таких как /dev/ttyUSB0. В большинстве дистрибутивов на основе Debian, включая Ubuntu и Raspberry Pi OS, эти узлы можно найти в /dev/serial/by-id.

Вы можете использовать такой путь к устройству вместо нумерованных сокращений. Вот пример TNC пакетной радиосвязи, настроенного таким образом:

[[Packet Radio KISS Interface]]
  type = KISSInterface
  interface_enabled = True
  outgoing = true
  port = /dev/serial/by-id/usb-FTDI_FT230X_Basic_UART_43891CKM-if00-port0
  speed = 115200
  databits = 8
  parity = none
  stopbits = 1
  preamble = 150
  txtail = 10
  persistence = 200
  slottime = 20

Использование этого метода позволяет избежать потенциальной путаницы имён, когда физические устройства могут подключаться и отключаться в разном порядке или когда назначение имён устройств меняется от одной загрузки к другой.

Reticulum как системная служба¶

Вместо того чтобы запускать Reticulum вручную, вы можете установить rnsd как системную службу и настроить её автоматический запуск при загрузке.

Общесистемная служба¶

Если вы установили Reticulum с помощью pip, программа rnsd, скорее всего, будет расположена только в пространстве пользователя, что означает, что systemd не сможет её выполнить. В этом случае вы можете просто создать символическую ссылку на программу rnsd в каталоге, который находится в пути systemd:

sudo ln -s $(which rnsd) /usr/local/bin/

Затем вы можете создать файл службы /etc/systemd/system/rnsd.service со следующим содержимым:

[Unit]
Description=Reticulum Network Stack Daemon
After=multi-user.target

[Service]
# Если вы запускаете Reticulum на устройствах WiFi
# или других устройствах, которым требуется
# дополнительное время для инициализации, возможно,
# вы захотите добавить небольшую задержку перед
# запуском Reticulum системой systemd:
# ExecStartPre=/bin/sleep 10
Type=simple
Restart=always
RestartSec=3
User=USERNAMEHERE
ExecStart=rnsd --service

[Install]
WantedBy=multi-user.target

Обязательно замените USERNAMEHERE на пользователя, от имени которого вы хотите запускать rnsd.

Чтобы вручную запустить rnsd, выполните:

sudo systemctl start rnsd

Если вы хотите автоматически запускать rnsd при загрузке, выполните:

sudo systemctl enable rnsd

Пользовательская служба¶

В качестве альтернативы вы можете использовать пользовательскую службу systemd вместо общесистемной. Таким образом, всю настройку можно выполнить от имени обычного пользователя. Создайте файл пользовательской службы systemd ~/.config/systemd/user/rnsd.service со следующим содержимым:

[Unit]
Description=Reticulum Network Stack Daemon
After=default.target

[Service]
# Если вы запускаете Reticulum на устройствах WiFi
# или других устройствах, которым требуется
# дополнительное время для инициализации, возможно,
# вы захотите добавить небольшую задержку перед
# запуском Reticulum системой systemd:
# ExecStartPre=/bin/sleep 10
Type=simple
Restart=always
RestartSec=3
ExecStart=RNS_BIN_DIR/rnsd --service

[Install]
WantedBy=default.target

Замените RNS_BIN_DIR на путь к вашему каталогу с исполняемыми файлами Reticulum (например, /home/USERNAMEHERE/rns/bin).

Запустите пользовательскую службу:

systemctl --user daemon-reload
systemctl --user start rnsd.service

Если вы хотите автоматически запускать rnsd без необходимости входа в систему как USERNAMEHERE, выполните:

sudo loginctl enable-linger USERNAMEHERE
systemctl --user enable rnsd.service
