Настройка интерфейсов¶

Reticulum поддерживает использование множества видов устройств в качестве сетевых интерфейсов и позволяет вам смешивать и сочетать их любым удобным вам способом. Количество различных сетевых топологий, которые вы можете создать с помощью Reticulum, более или менее бесконечно, но общим для всех них является то, что вам нужно будет определить один или несколько интерфейсов для использования Reticulum.

В следующих разделах описаны интерфейсы, доступные в настоящее время в Reticulum, и приведены примеры конфигураций для соответствующих типов интерфейсов.

Для высокоуровневого обзора того, как можно формировать сети через различные типы интерфейсов, взгляните на главу Построение сетей этого руководства.

Пользовательские интерфейсы¶

В дополнение к встроенным типам интерфейсов, Reticulum полностью расширяем с помощью пользовательских интерфейсов, предоставляемых пользователями или сообществом, и создание пользовательских модулей интерфейсов несложно. Пожалуйста, смотрите пример пользовательского интерфейса для базового кода интерфейса, на основе которого можно строить.

Автоинтерфейс (Auto Interface)¶

AutoInterface обеспечивает связь с другими обнаруживаемыми узлами Reticulum через любые локальные среды на основе Ethernet или WiFi. Несмотря на то, что он использует IPv6 для обнаружения пиров и UDP для транспортировки пакетов, он не требует какой-либо функциональной IP-инфраструктуры, такой как маршрутизаторы или DHCP-серверы, в вашей физической сети.

Предупреждение

Если на вашем компьютере работает брандмауэр, он может блокировать трафик, необходимый для работы AutoInterface. В этом случае вам нужно будет разрешить UDP-трафик на портах 29716 и 42671.

Пока между пирами присутствует хотя бы какая-то коммутирующая среда (проводной коммутатор, хаб, точка доступа WiFi или аналогичное устройство, или просто два устройства, соединённые напрямую Ethernet-кабелем), он будет работать без какой-либо настройки, конфигурации или промежуточных устройств.

Для работы обнаружения пиров AutoInterface также требуется, чтобы в вашей системе была доступна поддержка локального IPv6, что должно быть по умолчанию во всех современных операционных системах, как настольных, так и мобильных.

Примечание

Почти всё современное оборудование Ethernet и WiFi будет работать без какой-либо настройки или конфигурации с AutoInterface, но небольшое подмножество устройств включает параметры, ограничивающие взаимодействие между устройствами по умолчанию, что приводит к блокировке обнаружения пиров AutoInterface. Эта проблема чаще всего встречается на очень дешёвых WiFi-роутерах, предоставляемых интернет-провайдерами, и иногда может быть отключена в конфигурации роутера.

# Этот пример демонстрирует минимальную настройку
# автоинтерфейса. Он позволит общаться со всеми
# другими достижимыми устройствами на всех пригодных
# физических устройствах на основе Ethernet, которые
# доступны в системе.
[[Интерфейс по умолчанию]]
  type = AutoInterface
  enabled = yes

# Этот пример демонстрирует более специфично
# настроенный автоинтерфейс, который использует
# только определённые физические интерфейсы и
# имеет ряд других установленных опций.
[[Интерфейс по умолчанию]]
  type = AutoInterface
  enabled = yes

  # Вы можете создать несколько изолированных
  # сетей Reticulum в одной физической LAN,
  # указав разные идентификаторы групп.
  group_id = reticulum

  # Вы также можете выбрать тип мультикаст-адреса:
  # temporary (по умолчанию, Временный Мультикаст-Адрес)
  # или permanent (Постоянный Мультикаст-Адрес)
  multicast_address_type = permanent

  # Вы также можете выбрать конкретно, какие
  # сетевые устройства ядра использовать.
  devices = wlan0,eth1

  # Или позволить AutoInterface использовать все
  # подходящие устройства, кроме списка игнорируемых.
  ignored_devices = tun0,eth0

Если вы подключены к Интернету через IPv6, и ваш провайдер маршрутизирует IPv6-мультикаст, вы потенциально можете настроить автоинтерфейс на глобальное автообнаружение других узлов Reticulum в пределах выбранного вами Group ID. Вы можете указать область обнаружения, установив её в одно из значений: link, admin, site, organisation или global.

[[Интерфейс по умолчанию]]
  type = AutoInterface
  enabled = yes

  # Настроить глобальное обнаружение

  group_id = custom_network_name
  discovery_scope = global

  # Другие параметры конфигурации

  discovery_port = 48555
  data_port = 49555

Магистральный интерфейс (Backbone Interface)¶

Магистральный интерфейс — это очень быстрый и ресурсоэффективный тип интерфейса, в первую очередь предназначенный для соединения экземпляров Reticulum через множество различных типов сред. Он использует бэкенд ввода-вывода на основе событий ядра и может обрабатывать тысячи интерфейсов и/или клиентов с относительно низкой утилизацией системных ресурсов. Этот тип интерфейса в настоящее время поддерживается только в Linux и Android.

Примечание

Магистральный интерфейс полностью совместим с типами TCPServerInterface и TCPClientInterface, и они могут использоваться взаимозаменяемо и перекрёстно подключаться друг к другу. В системах, поддерживающих BackboneInterface, обычно рекомендуется использовать его, если вам не нужны специфические опции или функции, которые предоставляют TCP-серверные и клиентские интерфейсы.

Хотя цель состоит в поддержке всех типов сокетов и устройств ввода-вывода, предоставляемых базовой операционной системой, первоначальный выпуск обеспечивает поддержку только TCP-соединений через IPv4 и IPv6.

Для всех типов соединений через BackboneInterface Reticulum будет корректно обрабатывать прерывистость, потерю связи и соединения, которые появляются и исчезают.

Слушатели¶

Следующие примеры иллюстрируют различные способы настройки слушателей BackboneInterface. 

# Этот пример демонстрирует магистральный интерфейс,
# который слушает входящие соединения на указанном
# IP-адресе и номере порта.
[[Магистральный Слушатель]]
  type = BackboneInterface
  enabled = yes
  listen_on = 0.0.0.0
  port = 4242

# В качестве альтернативы вы можете привязаться к
# конкретному IP-адресу
[[Магистральный Слушатель]]
  type = BackboneInterface
  enabled = yes
  listen_on = 10.0.0.88
  port = 4242

# Или к конкретному сетевому устройству
[[Магистральный Слушатель]]
  type = BackboneInterface
  enabled = yes
  device = eth0
  port = 4242

Если вы используете интерфейс на устройстве, которое имеет доступные адреса как IPv4, так и IPv6, вы можете использовать опцию prefer_ipv6 для привязки к IPv6-адресу:

# Этот пример демонстрирует магистральный интерфейс,
# слушающий на IPv6-адресе указанного сетевого
# устройства ядра.
[[Магистральный Слушатель]]
  type = BackboneInterface
  enabled = yes
  prefer_ipv6 = yes
  device = eth0
  port = 4242

Чтобы использовать BackboneInterface поверх Yggdrasil, вы можете просто указать устройство tun Yggdrasil и порт для прослушивания, например: 

# Этот пример демонстрирует магистральный интерфейс,
# слушающий соединения через Yggdrasil.
[[Yggdrasil Магистральный Интерфейс]]
  type = BackboneInterface
  enabled = yes
  device = tun0
  port = 4343

Подключение удалённых узлов¶

Следующие примеры иллюстрируют различные способы подключения к удалённым слушателям BackboneInterface. Как отмечалось выше, интерфейсы BackboneInterface также могут подключаться к удалённым TCPServerInterface, и поэтому эти типы интерфейсов могут использоваться взаимозаменяемо.

# Вот пример магистрального интерфейса, который
# подключается к удалённому слушателю.
[[Магистральный Удалённый]]
  type = BackboneInterface
  enabled = yes
  remote = amsterdam.connect.reticulum.network
  target_port = 4251

Для подключения к удалённым узлам через Yggdrasil просто укажите целевой IPv6-адрес Yggdrasil и порт, например:

[[Yggdrasil Удалённый]]
    type = BackboneInterface
    enabled = yes
    target_host = 201:5d78:af73:5caf:a4de:a79f:3278:71e5
    target_port = 4343

Интерфейс TCP-сервера¶

Интерфейс TCP-сервера подходит для того, чтобы позволить другим пирам подключаться через Интернет или частные сети IPv4 и IPv6. Когда интерфейс TCP-сервера настроен, другие пиры Reticulum могут подключаться к нему с помощью интерфейса TCP-клиента.

# Этот пример демонстрирует интерфейс TCP-сервера.
# Он будет слушать входящие соединения на всех IP-
# интерфейсах на порту 4242.
[[Интерфейс TCP-сервера]]
  type = TCPServerInterface
  enabled = yes
  listen_ip = 0.0.0.0
  listen_port = 4242

# В качестве альтернативы вы можете привязаться к
# конкретному IP-адресу
[[Интерфейс TCP-сервера]]
  type = TCPServerInterface
  enabled = yes
  listen_ip = 10.0.0.88
  listen_port = 4242

# Или к конкретному сетевому устройству
[[Интерфейс TCP-сервера]]
  type = TCPServerInterface
  enabled = yes
  device = eth0
  listen_port = 4242

Если вы используете интерфейс на устройстве, которое имеет доступные адреса как IPv4, так и IPv6, вы можете использовать опцию prefer_ipv6 для привязки к IPv6-адресу:

# Этот пример демонстрирует интерфейс TCP-сервера.
# Он будет слушать входящие соединения на указанном
# IP-адресе и номере порта.

[[Интерфейс TCP-сервера]]
  type = TCPServerInterface
  enabled = yes
  prefer_ipv6 = True
  device = eth0
  port = 4242

Чтобы использовать интерфейс TCP-сервера через Yggdrasil, вы можете просто указать устройство tun Yggdrasil и порт для прослушивания, например:

[[Yggdrasil Интерфейс TCP-сервера]]
  type = TCPServerInterface
  enabled = yes
  device = tun0
  listen_port = 4343

Примечание

Интерфейсы TCP поддерживают туннелирование через I2P, но для надёжной работы необходимо использовать опцию i2p_tunneled:

[[TCP Сервер через I2P]]
  type = TCPServerInterface
  enabled = yes
  listen_ip = 127.0.0.1
  listen_port = 5001
  i2p_tunneled = yes

Почти во всех случаях проще использовать выделенный I2PInterface, но для полного контроля и использования I2P-роутеров, работающих на внешних системах, эта опция также существует.

Интерфейс TCP-клиента¶

Для подключения к интерфейсу TCP-сервера вы можете использовать интерфейс TCP-клиента. Множество интерфейсов TCP-клиентов от разных пиров могут одновременно подключаться к одному и тому же интерфейсу TCP-сервера.

Типы интерфейсов TCP также могут переносить прерывистость на уровне IP-соединения. Это означает, что Reticulum будет корректно обрабатывать IP-соединения, которые появляются и исчезают, и восстанавливать связь после сбоя, как только другой конец TCP-интерфейса снова появится.

# Вот пример интерфейса TCP-клиента. target_host
# может быть именем хоста или IPv4, или IPv6 адресом.
[[Интерфейс TCP-клиента]]
  type = TCPClientInterface
  enabled = yes
  target_host = 127.0.0.1
  target_port = 4242

Чтобы использовать интерфейс TCP-клиента через Yggdrasil, просто укажите целевой IPv6-адрес Yggdrasil и порт, например:

[[Yggdrasil Интерфейс TCP-клиента]]
    type = TCPClientInterface
    enabled = yes
    target_host = 201:5d78:af73:5caf:a4de:a79f:3278:71e5
    target_port = 4343

Также можно использовать этот тип интерфейса для подключения через другие программы или аппаратные устройства, которые предоставляют интерфейс KISS на TCP-порту, например, программные звуковые модемы. Для этого используйте опцию kiss_framing:

# Вот пример интерфейса TCP-клиента, который подключается
# к программному TNC звуковому модему через порт KISS поверх TCP.

[[TCP KISS Интерфейс]]
  type = TCPClientInterface
  enabled = yes
  kiss_framing = True
  target_host = 127.0.0.1
  target_port = 8001
  fixed_mtu = 500

Осторожно! Используйте опцию KISS framing только при подключении к внешним устройствам и программам, таким как звуковые модемы и подобные, через TCP. При использовании TCPClientInterface совместно с TCPServerInterface никогда не следует включать kiss_framing, так как это отключит внутренние механизмы надёжности и восстановления, которые значительно улучшают производительность через ненадёжные и прерывистые TCP-соединения.

Для KISS-устройств, которые поддерживают только определённый MTU, вы можете использовать опцию fixed_mtu.

Примечание

Интерфейсы TCP поддерживают туннелирование через I2P, но для надёжной работы необходимо использовать опцию i2p_tunneled:

[[TCP-клиент через I2P]]
    type = TCPClientInterface
    enabled = yes
    target_host = 127.0.0.1
    target_port = 5001
    i2p_tunneled = yes

Интерфейс UDP¶

Интерфейс UDP может быть полезен для связи через IP-сети, как частные, так и через Интернет. Он также может обеспечивать широковещательную связь через IP-сети, поэтому он может предоставить простой способ включить связь со всеми другими пирами в локальной сети.

Предупреждение

Использование широковещательного UDP-трафика имеет последствия для производительности, особенно на WiFi. Если ваша цель просто обеспечить лёгкую связь со всеми пирами в вашем локальном широковещательном домене Ethernet, автоинтерфейс работает гораздо лучше и даже проще в использовании.

# Этот пример включает связь с другими локальными
# пирами Reticulum через UDP.

[[UDP Интерфейс]]
  type = UDPInterface
  enabled = yes

  listen_ip = 0.0.0.0
  listen_port = 4242
  forward_ip = 255.255.255.255
  forward_port = 4242

  # Приведённая выше конфигурация позволит общаться
  # в пределах локальных широковещательных доменов
  # всех локальных IP-интерфейсов.

  # Вместо указания listen_ip, listen_port,
  # forward_ip и forward_port, вы также можете
  # привязаться к конкретному сетевому устройству,
  # как показано ниже.

  # device = eth0
  # port = 4242

  # Предполагая, что устройство eth0 имеет адрес
  # 10.55.0.72/24, приведённая выше конфигурация была бы
  # эквивалентна следующей ручной настройке.
  # Обратите внимание, что мы одновременно слушаем и
  # пересылаем на широковещательный адрес сетевых сегментов.

  # listen_ip = 10.55.0.255
  # listen_port = 4242
  # forward_ip = 10.55.0.255
  # forward_port = 4242

  # Вы, конечно, также можете общаться только с
  # одним IP-адресом

  # listen_ip = 10.55.0.15
  # listen_port = 4242
  # forward_ip = 10.55.0.16
  # forward_port = 4242

Интерфейс I2P¶

Интерфейс I2P позволяет соединять экземпляры Reticulum через Протокол Невидимого Интернета. Это может быть особенно полезно в случаях, когда вы хотите разместить глобально доступный экземпляр Reticulum, но не имеете доступа к публичным IP-адресам, имеете часто меняющийся IP-адрес или брандмауэры, блокирующие входящий трафик.

Используя интерфейс I2P, вы получите глобально доступный, портативный и постоянный I2P-адрес, по которому можно связаться с вашим экземпляром Reticulum.

Для использования интерфейса I2P у вас должен быть запущен I2P-роутер в вашей системе. Самый простой способ добиться этого — загрузить и установить последнюю версию пакета i2pd. Для получения более подробной информации об I2P смотрите веб-сайт geti2p.net.

Когда I2P-роутер работает в вашей системе, вы можете просто добавить интерфейс I2P в Reticulum:

[[I2P]]
  type = I2PInterface
  enabled = yes
  connectable = yes

При первом запуске Reticulum сгенерирует новый I2P-адрес для интерфейса и начнёт прослушивать входящий трафик на нём. Это может занять некоторое время в первый раз, особенно если ваш I2P-роутер также был только что запущен и ещё не имеет хороших связей с сетью I2P. Когда всё будет готово, вы должны увидеть I2P base32 адрес, выведенный в ваш лог-файл. Вы также можете проверить состояние интерфейса с помощью утилиты rnstatus.

Чтобы подключиться к другим экземплярам Reticulum через I2P, просто добавьте список I2P base32 адресов, разделённых запятыми, в опцию peers интерфейса:

[[I2P]]
  type = I2PInterface
  enabled = yes
  connectable = yes
  peers = 5urvjicpzi7q3ybztsef4i5ow2aq4soktfj7zedz53s47r54jnqq.b32.i2p

Установление I2P-соединений с желаемыми пирами может занять от нескольких секунд до нескольких минут, поэтому Reticulum обрабатывает процесс в фоновом режиме и будет выводить соответствующие события в лог.

Примечание

Хотя интерфейс I2P является самым простым способом использования Reticulum через I2P, также возможно туннелировать интерфейсы TCP-сервера и клиента через I2P вручную. Это может быть полезно в ситуациях, когда требуется больше контроля, но требует ручной настройки туннеля через конфигурацию демона I2P.

Важно отметить, что эти два метода взаимозаменяемо совместимы. Вы можете использовать I2PInterface для подключения к TCPServerInterface, который был вручную туннелирован через I2P, например. Это предлагает высокую степень гибкости в настройке сети, сохраняя при этом простоту использования в более простых случаях.

Интерфейс RNode LoRa¶

Для использования Reticulum через LoRa можно использовать интерфейс RNode, который предлагает полный контроль над параметрами LoRa.

Предупреждение

Интерфейс Pipe¶

Используя этот интерфейс, Reticulum может использовать любую программу в качестве интерфейса через stdin и stdout. Это можно использовать для лёгкого создания виртуальных интерфейсов или для взаимодействия с нестандартным оборудованием или другими системами.

[[Интерфейс Pipe]]
  type = PipeInterface
  enabled = yes

  # Внешняя команда для выполнения
  command = netcat -l 5757

  # Необязательная задержка перезапуска в секундах
  respawn_delay = 5

Reticulum будет записывать все пакеты в stdin опции command и будет непрерывно читать и сканировать её stdout на наличие пакетов Reticulum. Если будет достигнут EOF, Reticulum попытается перезапустить программу после ожидания в течение respawn_interval секунд.

Обнаруживаемые интерфейсы¶

Reticulum включает мощную систему для публикации ваших локальных интерфейсов в более широкую сеть, позволяя другим пирам обнаруживать, проверять и автоматически подключаться к ним. Эта функция особенно полезна для создания децентрализованных сетей, где пиры могут динамически находить точки входа, такие как публичные интернет-шлюзы или локальные точки радиодоступа, не полагаясь на статические файлы конфигурации или централизованные каталоги.

Когда интерфейс делается обнаруживаемым, ваш экземпляр Reticulum будет периодически рассылать объявление, содержащее детали подключения и параметры, необходимые другим пирам для установления соединения. Эти объявления распространяются по сети с использованием стандартного механизма объявлений Reticulum, используя тип назначения rnstransport.discovery.interface.

Примечание

Для использования функциональности обнаружения интерфейсов модуль LXMF должен быть установлен в вашем окружении Python. Вы можете установить его с помощью pip: 

pip install lxmf

Включение обнаружения¶

Обнаружение интерфейсов включается на основе каждого интерфейса. Чтобы сделать конкретный интерфейс обнаруживаемым, вы должны добавить опцию discoverable в блок конфигурации этого интерфейса и установить её в yes.

[[Мой Публичный Шлюз]]
  type = BackboneInterface
  ...
  discoverable = yes

После включения Reticulum будет автоматически обрабатывать генерацию, подпись, штамповку и широковещательную рассылку объявлений об обнаружении. Не требуется включать транспорт для публикации информации об обнаружении интерфейса, но для большинства случаев использования, когда вы хотите, чтобы другие подключались к вам, вы, вероятно, захотите установить enable_transport в yes в секции [reticulum] вашей конфигурации.

Параметры обнаружения¶

Когда discoverable включён, становится доступным множество дополнительных опций для управления тем, как интерфейс представляется сети. Эти параметры позволяют вам точно настроить метаданные, требования безопасности и видимость вашего интерфейса.

Основные метаданные

discovery_name

Человекочитаемое имя для интерфейса. Это имя будет отображаться пользователям на удалённых системах при просмотре списка обнаруженных интерфейсов. Если не указано, будет использоваться имя интерфейса (заголовок секции).

announce_interval

Интервал в минутах между последовательными объявлениями об обнаружении для этого интерфейса. По умолчанию 360 минут (6 часов). Для стабильной, долго работающей инфраструктуры большие интервалы (от 12 до 22 часов) обычно достаточны и снижают нагрузку на сеть. Минимальное допустимое значение — 5 минут (но ожидайте, что ваши объявления будут замедлены, если использовать интервалы менее одного часа).

Спецификация подключения

reachable_on

Указывает адрес, который удалённые пиры должны использовать для подключения к этому интерфейсу.

  • Для интерфейсов TCP и Backbone это обычно публичный IP-адрес или имя хоста. Не указывайте порт, он берётся автоматически из интерфейса.

  • Для интерфейсов I2P это обычно I2P-адрес b32. Это значение берётся автоматически из I2PInterface, как только он запущен и подключён к сети I2P, поэтому вам не следует устанавливать его вручную, если вы абсолютно не уверены в том, что делаете.

Динамическое разрешение: Эта опция также принимает путь к внешнему исполняемому скрипту или бинарному файлу. Если указан путь, Reticulum выполнит скрипт и использует его stdout в качестве адреса достижимости. Это полезно для устройств за динамическим DNS, NAT или в сложных облачных средах, где внешний IP-адрес неизвестен локально. Скрипт должен просто вывести адрес в stdout и завершиться.

Примечание

При использовании исполняемого скрипта для reachable_on Reticulum ожидает, что скрипт выведет в stdout только IP-адрес или имя хоста, за которым следует символ новой строки. Любой дополнительный вывод или ошибки могут привести к сбою разрешения. Убедитесь, что скрипт имеет права на выполнение и устойчив к временным сетевым сбоям.

Минимальный пример скрипта, который разрешает внешне доступный, публичный IP-адрес системы, подключённой к Интернету, может выглядеть так:

#!/bin/bash
curl -s ip.me
exit $?

В реальной системе вы должны сделать скрипт достаточно надёжным, чтобы справляться с периодическими сбоями Интернета или сервиса, чтобы скрипт всегда возвращал разумное значение, или, если это невозможно, по крайней мере завершался с ненулевым кодом возврата, чтобы Reticulum знал, что вывод недействителен.

Безопасность и стоимость

discovery_stamp_value

Определяет сложность доказательства работы для криптографического штампа, включённого в объявление. Это значение действует как барьер стоимости для предотвращения флуда в сети. Значение по умолчанию — 14. Увеличение этого значения делает вычислительно более затратным создание объявления, что может быть полезно для предотвращения спама в очень больших сетях, но также увеличивает нагрузку на процессор вашей системы при создании объявлений. Штампы кешируются и генерируются только при изменении информации об интерфейсе или при перезапуске экземпляра. Если у вас есть вычислительные ресурсы, обычно рекомендуется использовать как можно более высокое значение штампа.

Приватность и шифрование

discovery_encrypt

Если установлено в yes, полезная нагрузка объявления об обнаружении будет зашифрована. Для расшифровки объявления удалённые пиры должны обладать сетевой идентичностью, настроенной для вашего экземпляра (см. network_identity в секции [reticulum]). Это позволяет вам публиковать частные интерфейсы, которые доступны для обнаружения только определённым доверенным сетям.

Важно

Если вы включите discovery_encrypt, но не настроите действительную network_identity в секции [reticulum] вашей конфигурации, Reticulum прервёт объявление об обнаружении интерфейса. Для работы шифрования требуется действительный ключ сетевой идентичности.

publish_ifac

Если установлено в yes, имя и парольная фраза Кода Доступа к Интерфейсу (IFAC) для этого интерфейса будут включены в объявление об обнаружении. Это позволяет пирам автоматически настраивать правильные параметры аутентификации при подключении к интерфейсу.

Физическое местоположение

latitude, longitude, height

Необязательные физические координаты для интерфейса. Они полезны для географического отображения обнаруженных интерфейсов или для автоматического выбора клиентами ближайшей точки доступа. Координаты должны быть в десятичных градусах, высота в метрах.

Радиопараметры

Для физических радиоинтерфейсов, таких как RNodeInterface или KISSInterface, следующие необязательные параметры позволяют вам передавать рабочую частоту и характеристики, позволяя клиентам проверять совместимость перед подключением:

discovery_frequency

Рабочая частота в Гц. Автоматически настраивается на интерфейсах RNode. Необходима на радиоинтерфейсах на основе KISS и TCPClientInterfaces, подключающихся к радиомодемам.

discovery_bandwidth

Полоса пропускания сигнала в Гц. Автоматически настраивается на интерфейсах RNode. Полезна на радиоинтерфейсах на основе KISS и TCPClientInterfaces, подключающихся к радиомодемам.

discovery_modulation

Тип или схема модуляции. Автоматически настраивается на интерфейсах RNode, но крайне рекомендуется к включению на других радиоинтерфейсах.

Режимы интерфейса¶

Когда вы включаете обнаружение на интерфейсе, Reticulum применяет определённые режимы интерфейса, чтобы гарантировать, что интерфейс действительно полезен для удалённых пиров.

Если интерфейс настроен как discoverable, но его режим явно не установлен в gateway (для серверных интерфейсов, таких как BackboneInterface или TCPServerInterface) или access_point (для радиоинтерфейсов, таких как RNodeInterface), Reticulum автоматически настроит соответствующий режим и запишет уведомление в лог.

Например, если вы включите обнаружение на RNodeInterface без указания режима, Reticulum автоматически установит его в режим access_point.

Вопросы безопасности¶

Делая интерфейсы обнаруживаемыми, вы фактически рассылаете приглашение подключиться к вашей системе. Важно понимать последствия для безопасности выбираемых вами опций конфигурации.

Публикация учётных данных

Если вы включите publish_ifac = yes, парольная фраза аутентификации вашего интерфейса будет включена в объявление. Если вы управляете публичной сетью и хотите, чтобы любой мог подключиться, это приемлемо. Однако, если вы хотите ограничить доступ определённой группой пользователей, вы должны включить discovery_encrypt = yes. Это гарантирует, что только пиры, обладающие правильной network_identity, смогут декодировать парольную фразу.

Раскрытие топологии

Обнаруживаемый интерфейс объявляет о своём присутствии, местоположении (если настроено) и возможностях всей сети. Даже если детали подключения зашифрованы, сам факт существования подключаемого узла в определённой сети становится публичной информацией. В сценариях с высокой степенью безопасности или требующих оперативной секретности, учитывайте последствия рекламы существования вашей инфраструктуры.

Пример конфигурации¶

Ниже приведён пример конфигурации для публичного магистрального шлюза. Эта конфигурация публикует высокоценный, публично обнаруживаемый интерфейс, к которому может подключиться любой.

[[Мой Публичный Шлюз]]
  type = BackboneInterface
  mode = gateway
  listen_on = 0.0.0.0
  port = 4242

  # Включить обнаружение
  discoverable = yes

  # Детали интерфейса
  discovery_name = Публичная Точка Входа Региона А
  announce_interval = 720

  # Использовать внешний скрипт для разрешения динамического IP
  reachable_on = /usr/local/bin/get_external_ip.sh

  # Сгенерировать высокое значение штампа
  discovery_stamp_value = 24

  # Необязательные данные о местоположении
  latitude = 51.99714
  longitude = -0.74195
  height = 15

Следующий пример создаёт зашифрованный интерфейс с включённым обнаружением, требующий определённой сетевой идентичности для декодирования, и включает учётные данные IFAC для бесшовной аутентификации.

[[Мой Частный Шлюз]]
  type = BackboneInterface
  mode = gateway
  listen_on = 0.0.0.0
  port = 5858
  network_name = internal_1
  passphrase = Mevpekyafshak5Wr

  # Включить обнаружение
  discoverable = yes

  # Детали интерфейса
  discovery_name = Частный Магистральный Канал Региона А
  announce_interval = 720

  # Использовать внешний скрипт для разрешения динамического IP
  reachable_on = /usr/local/bin/get_external_ip.sh

  # Целевое значение штампа
  discovery_stamp_value = 22

  # Шифровать объявления только для нашей сети
  discovery_encrypt = yes

  # Включить учётные данные, чтобы доверенные
  # пиры могли подключаться автоматически
  publish_ifac = yes

  # Необязательные данные о местоположении
  latitude = 34.06915
  longitude = -118.44318
  height = 15

В секции [reticulum] вашей конфигурации вы должны определить сетевую идентичность, используемую для шифрования, следующим образом:

[reticulum]
...
# Идентичность, используемая для подписи/шифрования объявлений об обнаружении
network_identity = ~/.reticulum/storage/identities/my_network_identity
...

С применением этих опций конфигурации ваш экземпляр Reticulum будет активно участвовать в экосистеме обнаружения сети. Другие пиры, работающие с Reticulum с включённым обнаружением, смогут видеть ваш интерфейс, проверять его криптографический штамп и (в зависимости от их конфигурации) автоматически подключаться к нему.

Для получения информации о том, как использовать эти обнаруженные интерфейсы и настроить вашу систему на автоматическое подключение к ним, обратитесь к главе Обнаружение интерфейсов.

Общие параметры интерфейсов¶

На большинстве интерфейсов доступен ряд общих параметров конфигурации. Их можно использовать для управления различными аспектами поведения интерфейса.

  • Опция enabled указывает Reticulum, следует ли поднимать интерфейс. По умолчанию False. Чтобы любой интерфейс был поднят, опция enabled должна быть установлена в True или Yes.
  • Опция mode позволяет выбрать высокоуровневое поведение интерфейса из ряда вариантов.

    • Значение по умолчанию — full. В этом режиме доступны все функции обнаружения, построения ячеистой сети и транспорта.

    • В режиме access_point (или сокращённо ap) интерфейс будет работать как точка доступа к сети. В этом режиме объявления не будут автоматически широковещательно передаваться на интерфейсе, а пути к назначениям на интерфейсе будут иметь гораздо более короткое время истечения. Этот режим полезен для создания интерфейсов, которые в основном молчат, за исключением случаев, когда кто-то действительно их использует. Примером этого может быть радиоинтерфейс, обслуживающий большую территорию, где пользователи, как ожидается, подключаются на короткое время, используют сеть, а затем снова исчезают.

  • Опция outgoing устанавливает, разрешено ли интерфейсу передавать данные. По умолчанию True. Если установлено в False или No, интерфейс будет только принимать данные и никогда не передавать.
  • Опция network_name устанавливает имя виртуальной сети для интерфейса. Это позволяет существовать нескольким отдельным сегментам сети на одном физическом канале или среде.
  • Опция passphrase устанавливает парольную фразу аутентификации на интерфейсе. Эта опция может использоваться совместно с опцией network_name или отдельно.
  • Опция ifac_size позволяет настроить длину Кодов Аутентификации Интерфейса, переносимых каждым пакетом в именованных и/или аутентифицированных сегментах сети. По умолчанию устанавливается размер, подходящий для данного интерфейса, но с помощью этой опции можно установить пользовательский размер от 8 до 512 бит. При нормальном использовании эту опцию не следует изменять по сравнению со значением по умолчанию.
  • Опция announce_cap позволяет настроить максимальную полосу пропускания, выделяемую в любой момент времени для распространения объявлений и другого трафика обслуживания сети. По умолчанию она настроена на 2%, и обычно не должна нуждаться в изменении. Может быть установлена в любое значение от 1 до 100.

    Если интерфейс превышает свой лимит объявлений, он будет ставить объявления в очередь для последующей передачи. Reticulum всегда будет отдавать приоритет распространению объявлений от близлежащих узлов в первую очередь. Это гарантирует, что локальная топология приоритизируется, и что медленные сети не будут перегружены взаимосвязанными быстрыми сетями.

    Назначения, которые быстро переобъявляются, будут дополнительно деприоритизированы. Попытка попасть «в начало очереди» путём спама объявлениями будет иметь прямо противоположный эффект: перемещение в конец очереди каждый раз при получении нового объявления от чрезмерно объявляющего назначения.

    Это означает, что всегда выгодно выбирать сбалансированную частоту объявлений и не объявлять чаще, чем это действительно необходимо для функционирования вашего приложения.

  • Опция bitrate настраивает скорость интерфейса. Reticulum будет использовать скорости интерфейса, сообщаемые оборудованием, или пытаться угадать подходящую скорость, когда оборудование ничего не сообщает. В большинстве случаев автоматически определённой скорости должно быть достаточно, но её можно настроить с помощью опции bitrate, чтобы установить скорость интерфейса в битах в секунду.
  • Опция bootstrap_only обозначает интерфейс как временный мост для начальной связности. Если эта опция включена, интерфейс будет отслеживаться и автоматически отключён, как только количество автоматически подключённых интерфейсов достигнет лимита, настроенного autoconnect_discovered_interfaces. Это особенно полезно для использования медленного или дорогого соединения (такого как единственная линия LoRa или удалённый TCP-туннель) исключительно для обнаружения лучшей локальной инфраструктуры, которая затем заменяет собой начальный интерфейс.

Режимы интерфейсов¶

Необязательная настройка mode доступна на всех интерфейсах и позволяет выбирать высокоуровневое поведение интерфейса из ряда режимов. Эти режимы влияют на то, как Reticulum выбирает пути в сети, как распространяются объявления, как долго действительны пути и как пути обнаруживаются.

Настройка режимов интерфейсов не является строго обязательной, но может быть полезна при построении или подключении к более сложным сетям. Если ваш экземпляр Reticulum не запускает Транспортный Узел, настройка режимов интерфейса редко бывает полезной, и в таких случаях интерфейсы, как правило, следует оставлять в режиме по умолчанию.

  • Режим по умолчанию — full. В этом режиме активированы все функции обнаружения, построения ячеистой сети и транспорта.
  • Режим gateway (или сокращённо gw) также имеет все доступные функции обнаружения, построения ячеистой сети и транспорта, но дополнительно будет пытаться обнаруживать неизвестные пути от имени других узлов, находящихся на интерфейсе gateway. Если Reticulum получает запрос пути для неизвестного назначения от узла на интерфейсе gateway, он попытается обнаружить этот путь через все остальные активные интерфейсы и переслать найденный путь запрашивающему.
    Если вы хотите позволить другим узлам широко разрешать пути или подключаться к сети через интерфейс, может быть полезно перевести его в этот режим. Создав цепочку интерфейсов gateway, другие узлы смогут немедленно обнаруживать пути к любому назначению вдоль цепочки.
    Пожалуйста, обратите внимание! Чтобы это работало, в режим gateway должен быть переведён интерфейс, обращённый к клиентам, а не интерфейс, обращённый к более широкой сети (для этого, однако, может быть полезен режим boundary).
  • В режиме access_point (или сокращённо ap) интерфейс будет работать как точка доступа к сети. В этом режиме объявления не будут автоматически широковещательно передаваться на интерфейсе, а пути к назначениям на интерфейсе будут иметь гораздо более короткое время истечения. Кроме того, запросы путей от клиентов на интерфейсе точки доступа будут обрабатываться так же, как и на интерфейсе gateway.
    Этот режим полезен для создания интерфейсов, которые остаются тихими до тех пор, пока кто-то действительно не начнёт их использовать. Примером этого может быть радиоинтерфейс, обслуживающий большую территорию, где пользователи, как ожидается, подключаются на короткое время, используют сеть, а затем снова исчезают.
  • Режим roaming следует использовать на интерфейсах, которые являются роуминговыми (физически мобильными), с точки зрения других узлов сети. Например, если транспортное средство оснащено внешним интерфейсом LoRa и внутренним интерфейсом на основе WiFi, который обслуживает устройства, движущиеся вместе с транспортным средством, внешний интерфейс LoRa должен быть настроен как roaming, а внутренний интерфейс можно оставить в режиме по умолчанию. С включённым транспортом такая настройка позволит всем внутренним устройствам связываться друг с другом и со всеми другими устройствами, доступными на стороне LoRa сети, когда они находятся в зоне действия. Устройства на стороне LoRa сети также смогут связываться с устройствами внутри транспортного средства, когда оно находится в зоне действия. Пути через roaming интерфейсы также истекают быстрее.
  • Цель режима boundary — указать интерфейсы, которые устанавливают связность с сегментами сети, значительно отличающимися от того, в котором существует данный узел. Например, если экземпляр Reticulum является частью сети на основе LoRa, но также имеет высокоскоростное соединение с публичным Транспортным Узлом, доступным в Интернете, интерфейс, подключающийся через Интернет, должен быть установлен в режим boundary.

Таблицу, описывающую влияние всех режимов на распространение объявлений, можно найти в разделе Правила распространения объявлений.

Контроль частоты объявлений¶

Встроенные механизмы контроля объявлений и опция announce_cap по умолчанию, описанная выше, достаточны в большинстве случаев, но в некоторых ситуациях, особенно на быстрых интерфейсах, может быть полезно контролировать целевую частоту объявлений. С помощью опций announce_rate_target, announce_rate_grace и announce_rate_penalty это можно сделать на основе каждого интерфейса, и это регулирует скорость, с которой полученные объявления повторно передаются на другие интерфейсы.

  • Опция announce_rate_target устанавливает минимальное количество времени в секундах, которое должно пройти между полученными объявлениями для любого одного назначения. Например, установка этого значения в 3600 означает, что объявления, полученные на этом интерфейсе, будут повторно передаваться и распространяться на другие интерфейсы только раз в час, независимо от того, как часто они получены.
  • Необязательная опция announce_rate_grace определяет, сколько раз назначение может нарушить целевую частоту объявлений, прежде чем целевая частота будет принудительно применена.
  • Необязательная опция announce_rate_penalty настраивает дополнительное количество времени, которое добавляется к обычной целевой частоте. Например, если определена пенальти в 7200 секунд, то как только целевая частота будет принудительно применена, рассматриваемое назначение будет иметь свои объявления распространёнными только каждые 3 часа, пока оно не снизит свою фактическую частоту объявлений до уровня в пределах целевой.

Эти механизмы, в сочетании с механизмами annouce_cap, упомянутыми выше, означают, что крайне важно выбирать сбалансированную стратегию объявлений для ваших назначений. Чем более сбалансированным вы сможете сделать это решение, тем легче вашим назначениям будет проникнуть в более медленные сети, находящиеся на расстоянии многих прыжков. Или вы можете отдать приоритет достижению только высокопроизводительных сетей с более частыми объявлениями.

Текущую статистику и информацию о частотах объявлений можно просмотреть с помощью команды rnpath -r.

Важно отметить, что не существует единственно правильного или неправильного способа настройки частот объявлений. Более медленные сети, естественно, будут стремиться к использованию менее частых объявлений для экономии пропускной способности, в то время как очень быстрые сети могут поддерживать приложения, которым нужны очень частые объявления. Reticulum реализует эти механизмы, чтобы гарантировать, что широкий спектр типов сетей может беспрепятственно сосуществовать и взаимодействовать.

Ограничение скорости новых назначений¶

На публичных интерфейсах, где любой может подключиться и объявить новые назначения, может быть полезно контролировать скорость, с которой обрабатываются объявления для новых назначений.

Если в течение короткого промежутка времени происходит большой приток объявлений для вновь созданных или ранее неизвестных назначений, Reticulum приостановит эти объявления, чтобы объявления для известных и ранее установленных назначений могли продолжать обрабатываться без перерывов.

После того как всплеск утихнет и пройдёт дополнительный период ожидания, приостановленные объявления будут выпускаться с низкой скоростью, пока очередь ожидания не очистится. Это также означает, что если узел решит подключиться к публичному интерфейсу, объявит большое количество фиктивных назначений, а затем отключится, эти назначения никогда не попадут в таблицы путей и не растратят пропускную способность сети на повторно переданные объявления.

Важно отметить, что контроль входящего трафика работает на уровне отдельных подинтерфейсов. Например, это означает, что один клиент на интерфейсе TCP-сервера не может нарушить обработку входящих объявлений для других подключённых клиентов на том же интерфейсе TCP-сервера. У всех других клиентов на том же интерфейсе новые объявления по-прежнему будут обрабатываться без перерыва.

По умолчанию Reticulum будет обрабатывать это автоматически, и контроль входящих объявлений будет включён на интерфейсах, где это целесообразно. Как правило, не должно требоваться изменять конфигурацию контроля входящих объявлений, но все параметры доступны для настройки в случае необходимости.

  • Опция ingress_control указывает Reticulum, следует ли включать контроль входящих объявлений на интерфейсе. По умолчанию True.
  • Опция ic_new_time настраивает, как долго (в секундах) интерфейс считается недавно созданным. По умолчанию 2*60*60 секунд. Эта опция полезна на публично доступных интерфейсах, которые порождают новые подинтерфейсы при подключении нового клиента.
  • Опция ic_burst_freq_new устанавливает максимальную частоту входящих объявлений для недавно созданных интерфейсов. По умолчанию 3.5 объявлений в секунду.
  • Опция ic_burst_freq устанавливает максимальную частоту входящих объявлений для других интерфейсов. По умолчанию 12 объявлений в секунду.

    Если интерфейс превышает свою частоту всплеска, входящие объявления для неизвестных назначений будут временно помещены в очередь и не будут обрабатываться до позже.

  • Опция ic_max_held_announces устанавливает максимальное количество уникальных объявлений, которые будут удерживаться в очереди. Любые дополнительные уникальные объявления будут отброшены. По умолчанию 256 объявлений.
  • Опция ic_burst_hold устанавливает, сколько времени (в секундах) должно пройти после того, как частота всплеска упадёт ниже своего порога, чтобы всплеск объявлений считался устранённым. По умолчанию 60 секунд.
  • Опция ic_burst_penalty устанавливает, сколько времени (в секундах) должно пройти после того, как всплеск считается устранённым, прежде чем удержанные объявления могут начать выпускаться из очереди. По умолчанию 5*60 секунд.
  • Опция ic_held_release_interval устанавливает, сколько времени (в секундах) должно пройти между выпуском каждого удержанного объявления из очереди. По умолчанию 30 секунд.
